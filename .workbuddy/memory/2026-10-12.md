## 2. 生产「渐变卡死、无报错、重启才好转」根因与修复
用户报：网关起初正常，逐渐等待非常久、无进度无报错，停了再开才恢复。
- 根因：客户端在流式首字节到达前断开（用户「停止」再继续）时，`web/server.go` 的 `proxy()` 流式分支 `case <-ctx.Done():` 直接 `return`，**无人消费后台 `relay.Do` 推入带缓冲 `ch` 的 `*Result`** → 其上游连接 + 并发信号量槽位永久泄漏。首选账号 sem 占满后所有请求卡在 `Acquire` 无限等待，只有重启能恢复。
- 修复：两处 `ctx.Done()` 都改为「起 goroutine 把 `ch` 里的 result 取出来 `Close()`（释放上游连接 + 信号量槽位）」：
  - 首字节等待窗口（原 1326 处 select）。
  - **心跳等待窗口**（1356 心跳循环 1387 处）——稳态长等待路径，比首字节窗口更易触发，原漏修，本次补上。
- 验证：`TestNeverLeaks429UnderBurst` 等 web 全绿；`go build ./...` 通过。
- 注：本次跑 `go test` 首次出现「测试超时」是冷启动偶发抖动（原始版连跑 3 次稳定 ~25s，我的改动连跑 3 次也稳定 ~25s；首个 60s 超时是编译后首跑异常），非回归。

## 5. 决定性 A/B 对照（09:35 用户实测）：卡死=客户端→网关连接路径，非网关逻辑也非上游
用户把 WorkBuddy 渠道从网关 `192.168.100.3:4142/v1` **切成官方 agnes 直连**（同一把账号 key，绕过网关）。结果：**速度没变快，但彻底不断流、不卡死**。
- 这等价于受控实验：同一账号、同一上游，只变「是否经网关」——直连正常 ⇒ 网关侧逻辑与上游延迟都无辜；卡死唯一变量是「客户端↔网关这一段连接」。
- 与 §4 互证：卡死是 09:14 我热更重启网关后，**WorkBuddy 连接池里的半死 keep-alive 连接**所致（请求写进黑洞、TCP 重传超时十几分钟）。直连用的是全新连接到官方，无此残留。
- 关键结论（需牢记）：
  1. 用户**原始**生产「渐变卡死」= v1.0.35 的信号量泄漏 bug（网关侧），**v1.0.36 已根治**。
  2. 部署后看到的「又卡死」= 我的重启留下的客户端半死连接，**是独立事件、非网关回归**。
  3. 网关对速度无附加开销（直连也未变快 ⇒ 慢在官方上游，与网关无关）。
- 网关侧现状：main.go:136 的 `&http.Server` 已设 `ReadHeaderTimeout=20s` / `ReadTimeout=5min` / `IdleTimeout=120s`，空闲连接 120s 服务端主动关；但「进程重启瞬间被杀、客户端仍以为活着的连接」服务端无法兜底，只能靠客户端重建连接池。
- **运维铁律（固化）**：任何网关 hot 重启前，必先提醒用户停掉在跑的任务；重启后让用户**重开会话或切模型再切回**以重建连接池，绝不在同会话直接续跑长任务。
