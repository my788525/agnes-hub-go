总体结论

调度内核（严格 FIFO 节拍 + 幂等/非幂等重试区分 + 账号×池二维自适应校准 + 熔断自动复活 + 粘性软溢出）设计成熟，已能支撑「客户端永不 429、任务不断线」的核心目标。 遗留风险集中在 挂机连续性：①流式长回答会被统一 30s 请求超时掐断；②全进程无 panic 恢复，任一路径 panic 会连正在跑的所有任务一起崩掉；③用量日志/绑定落盘随挂机时长线性膨胀。 这三项是当前「长期挂机无人干预」最可能触发中断的断点，建议优先修。

P0 · 挂机中断的高危断点

P0-1 流式长回答被统一 30s 请求超时掐断 响应速度 / 不断流

relay.go:289-296 的 attemptOnce 对所有请求（含 stream=true 的 SSE）统一套 RequestTimeoutMS（默认 30000ms）的 reqCtx 超时。上游是长文本回答时，SSE 流持续输出往往远超 30s；一旦 reqCtx 到期，流被取消、连接断开，客户端在长回答中途看到「断流」。 而 relay.Options 没有「是否流式」标志，attemptOnce 无法对流式做超时放宽。httpSrv 本身刻意不设 WriteTimeout（main.go:123-125），说明「长流」是预期支持的——问题只在上游侧的请求超时没区分流式。

建议
  • 给 relay.Options 增加 Stream bool；流式时把 RequestTimeoutMS 解释为「首字节/心跳空闲超时」而非「整请求墙钟超时」——即上游只要还在吐数据就持续重置空闲计时，真正卡死（长时间零字节）才断开。非流式保持现有 30s 整请求超时不变。
  • 流式空闲超时可单设一个更宽松的配置项（如 StreamIdleTimeoutMS，默认 60s）。
  • 影响面：仅 finishStream / proxy 流式路径；非流式行为零变化，回归风险低。

P0-2 全进程无 panic 恢复，单点 panic 会带走所有在途任务 鲁棒性 / 挂机

server.go:62-63 的 ServeHTTP 直接转发 s.mux，全仓（grep recover() 为空）没有任何 recover 中间件。标准库 net/http 对每个请求 goroutine 内 panic 会打印堆栈并关闭该连接，但像 server.go:1150 里 go func(){ relay.Do(...) ; ch<-... } 这种独立 goroutine 若 panic，会直接终止整个进程——正在跑的所有请求、排队中的任务、粘性会话全部蒸发。对「长期挂机」这是最致命的单点。

建议
  • 在 ServeHTTP 最外层包一层 defer func(){ if e:=recover(); e!=nil{ log + 500 } }()，兜住 handler 路径。
  • 给独立 goroutine（流式 relay.Do 的 goroutine、维护循环、更新器循环）各自加 recover，panic 时记录 debug.Stack() 并走优雅降级，而非进程级崩溃。
  • 可选（进阶）：加 /metrics 里的 panics_total 计数与日志落盘，便于挂机期间事后定位。
  • 影响面：纯加固，不改正常逻辑，是「挂机无人值守」的地基。
P1 · 长期挂机质量与可观测性

P1-1 用量日志 / 粘性绑定随挂机时长无限膨胀 挂机 / 存储

AppendUsage（config.go:1321）每次 done 请求向 usage.jsonl 追加一行且无轮转/上限；user_request 字段最多带 8KB。挂机 7×24 时该文件线性增长，最终磁盘占满。Bindings 有 TTL 清理（SessionTTLHours 默认 72h，config.go:1065-1072），这块是好的；但 usage.jsonl 与 videos.jsonl/images.jsonl 缺同样的轮转。

建议
  • 给 usage.jsonl 加按大小/按天数轮转（保留最近 N 天或 M MB，超出即截断），启动时检查一次。
  • 更省的做法：把 8KB 的 user_request 默认只记前 512B，控制台「查看完整请求」再按需从内存环形缓冲取——既保留排障能力又止住磁盘膨胀。
  • 影响面：仅日志/存储层，调度零影响。

P1-2 自更新会重启进程，正挂机长任务会被打断 不断流 / 挂机

自动更新链路：main.go:101-116 检测到 NeedRestart() 即 cancel() 触发优雅关闭；StartBackground（updater.go:324）每 12h Check，控制台手动 POST /api/update/apply（console.go:1680）才真正 Apply+RequestRestart。重启瞬间未完成的视频轮询、排队中的请求、流式回答都会中断。fnOS 上应用中心升级也走同类替换。对「挂机长跑」场景，更新时机不可控是现实的断点。

建议
  • 优雅关闭前拒绝新任务、等在途 in-flight 清零（或给一个有上限的宽限期）再退出，避免半途砍断。可在关闭钩子里轮询 h.inflight 总和，>0 则等待直至上限。
  • 视频类长任务加「恢复」语义：重启后 videos.jsonl 里的 submitted 任务仍可由客户端凭 job_id 续查（网关已有 handleVideoPoll，需确保 job 记录跨重启可用）。
  • 影响面：只改停机/升级时序，正常运行零变化。

P1-3 429 后因子下调依赖 Reload，节流收紧不够即时可观测 调度鲁棒性

OnRateLimited（hub.go:792）下调 poolFactors 后调 h.Reload()，Reload 内 p.Reconfigure(rpm, ...) 确实会夹紧 nextFreeAt（保留排队、不重建）。逻辑正确。但两点可改进：① 高频 429 风暴时每次 OnRateLimited 都全量 Reload（遍历全部账号×池×模态、读 AccountsSnapshot 深拷贝），CPU 与锁竞争偏高；② Reconfigure 只在因子变化时才 Reconfigure，若已到底（min_learned_factor=0.5）仍会空跑。

建议
  • 把「429 → 只收紧该 (账号×池) 一个 pacer」独立成 h.ReloadPacer(a, poolClass)，避免全量 Reload；全量 Reload 保留给设置变更/账号增删。
  • 在 /metrics 增加 breaker_open_total、upstream_429_rate_per_min、各账号当前 effective RPM gauge，让「挂机期间调度是否健康」可被外部监控告警。
  • 影响面：内部重构，行为保持一致，需回归 429 相关测试。

P1-4 挂机期缺少「健康心跳 + 自愈」闭环的对外出口 可观测性

当前有 /healthz 与 /metrics（文本，server.go:372 起），但「能否长期挂机」的判断缺少一个明确的聚合健康信号：比如「有 ≥1 个账号可用 + 最近 N 分钟成功率 + 队列积压」。外部编排（如 Docker/fnOS 的重启策略、Prometheus 告警）难以据此做自动拉起。

建议
  • 在 /healthz 返回富健康度：{ok, available_accounts, queue_depth, last_success_age_ms, breaker_open}，让外部可据此判断「该重启/告警」。
  • 可选加 self_health.jsonl 滚动记录，供事后审计挂机期间的退化曲线。
  • 影响面：只扩展只读端点，风险极低。
P2 · 响应速度与执行效率优化

P2-1 视频/图片提交绕过 pacer，靠独立 GET 轮询 效率

pollUpstream（server.go:943）用独立 GET /agnesapi?video_id= 轮询上游，不占生成配额、不进 pacer——这是对的（轮询本不该挤占生成 RPM）。但每轮 http.NewRequestWithContext + s.Client.Do 虽走共享连接池，仍逐次建 http.Request；高频轮询（间隔最小 1s）下可考虑复用 URL 构造、批量并发轮询多个 job。

建议
  • 多 job 挂机时用一个后台轮询器并发探测（带每账号并发上限），而非每个 job 各自起 goroutine；结果写回 videos.jsonl，客户端拉取即得，无需长连接占位。
  • 可选：指数拉大轮询间隔（前 30s 每 2s，之后每 5s/10s），显著降低挂机期上游探测压力。

P2-2 handleTextish 每请求重复 readBody + json.Marshal 克隆 速度

server.go:588-593：非 auto 模型路径对 body 做 cloneBody + json.Marshal 生成 buf；auto 路径走 bodyForAccount 每账号再 marshal 一次。热路径上 map→JSON 编解码与深拷贝是主要 CPU 开销。意图判定已走 LRU 缓存（intent/cache.go），这块已优化。

建议
  • 当 BodyFor 未改写 model 时，直接复用客户端原始 rawBody（readBody 已保留），省一次 marshal；仅确需改写 model 时才克隆。
  • 影响面：请求构造路径，需核对各模型别名/manifest 改写正确性。

P2-3 上游连接池上限偏低（高并发挂机） 效率

BuildClient（relay.go:52）：MaxIdleConns=200 / MaxIdleConnsPerHost=60。多账号（每个账号=独立 Host）挂机时，账号数 >60 会让每账号空闲连接被 60 截断，新连接重复 TLS 握手，抬高首字节延迟。

建议
  • 按「账号数」动态调 MaxIdleConnsPerHost（如 max(60, 账号数×并发)），或把连接池配置暴露到设置项。
  • 影响面：连接池参数，低风险。

P2-4 OnRateLimited 每 429 触发 Reload 全量快照 效率

与 P1-3 同根：429 风暴期全量 Reload（AccountsSnapshot 深拷贝所有账号）在锁内执行，放大 hub.mu 争用，间接拖慢并发请求的 Pick/Acquire。热路径本已用 MutateAccountNoSave 避免写盘（设计很好）。

建议
  • 429 路径只 ReloadPacer 单账号（见 P1-3），不触发全量快照。FlushAccounts 仍由 30s 维护循环批量落盘。
