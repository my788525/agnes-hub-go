1总体设计：一张图看懂

示意图：负载率滚动曲线（每秒右移一格，绿色 <70%、黄色 70–100%、红线 = 池容量打满）。实际页面共三块图，见第 3 节。

  • 后端：新增采样器 goroutine，每 1s 把「负载率 / 吞吐 / 排队 / 每账号完成数」拍一个快照进双环形缓冲（细窗口 10 分钟 @1s + 粗窗口 1 小时 @10s），暴露 GET /api/metrics-history。
  • 前端：console.html 新增「监控」tab，内嵌一个 ~120 行的自绘 canvas 图表引擎（无第三方库，保持 go:embed 零依赖约定），1s 轮询 history 端点，滚动重绘。资源管理器就是这个原理：CPU 采样 + 1s 重画。
  • 既有卡片不动：总览的到达密度直方图、KPI 卡保留，动态图表是新 tab + 总览底部一个 60s 缩略版入口。

2后端：metricsHistory 采样器（新文件 internal/hub/history.go）

2.1 每秒快照字段（一个 point）

字段口径来源（复用现有）
ts秒级时间戳time.Now()
load_pct负载百分比 = 到达速率 ÷ 池容量；容量 = Σ(启用账号 text RPM) / 60（req/s）arrivalRing.Counts() + pacer RPM（与现有 ratio 同口径，×100）
arrive_rps到达 req/s（当前秒）arrivalRing per_second 末位
done_rps完成 req/s（成功完成差分）Metrics.RequestsOK 计数器差分
queue_depth排队深度 = Σ 各池 waitingpacer.Waiting()
inflight在途请求总数Σ Inflight(account)
r429_per_min最近 60s 上游 429Recent429.PerMinute()
acc[]每启用账号：{id, inflight, done_delta}（done_delta = 该账号本秒完成数差分，供分配占比）账号 Stats 计数器差分

2.2 存储：双环形缓冲（内存上界 < 100KB）

窗口采样间隔点数覆盖用途
fine1s60010 分钟默认视图（60s/300s 可切）
coarse10s（fine 满时自动降采样挪入）3601 小时「时」视图
  • 单 goroutine（采样器）写 + 读加锁；采样器挂在现有维护循环旁边，进程空闲时照常采（画出来的平线本身就是信息）。
  • 账号增删：新账号从 0 起记录；删掉的账号历史点保留，前端标注「已移除」并折叠成灰色。分配占比按 done_delta / Σdone_delta 归一化，天然不受账号数变化影响。

2.3 端点

GET /api/metrics-history?win=fine|coarse —— 鉴权同现有 console API；返回 {points:[...], accounts:[{id,name,color}]}。fine 全量 ~600 点 × 每点约 100 字节 JSON ≈ 60KB，轮询每次只回最近 N 点（按视图窗口裁剪），实际 1s 拉取约 2–6KB，NAS 本地无压力。

为什么轮询而不是 SSE/WebSocket：与现有 api() 封装、鉴权、断线重连逻辑完全一致，零新基础设施；控制台是单管理员场景，1s 轮询的代价可忽略。SSE 留作后续优化项，不阻塞本期。

3前端：监控 tab + 自绘 canvas 引擎（console.html）

3.1 图表引擎（~120 行）

  • 一个 RollingChart 类：输入点数组 + 系列定义（颜色/线型/面积），canvas 按设备像素比渲染；网格背景、右侧当前值标签、Y 轴自适应刻度——任务管理器同款视觉。
  • 滚动手感：每秒整体左移一格（数据 shift），不做平滑插值动画——与资源管理器行为一致，实现最简、最省电。
  • 窗口切换：60s / 5min / 1h 三个 pill 按钮，切 fine/coarse 数据源。

3.2 三块图

图系列读法
① 负载率 %（核心）load_pct 面积线；100% 红虚线长期 <70% = 账号有余量；顶到 100% = 该加账号/调 RPM 了；抖到 100% 以上回落 = 排队在兜底
② 处理规模arrive_rps（蓝线）+ done_rps（绿线）+ queue_depth（黄色面积，右轴）+ inflight（紫线）蓝绿线贴合 = 没积压；黄面积鼓包 = 排队在削峰；inflight 是同时在跑的请求数
③ 多账号分配（堆叠面积）每账号一个颜色的 done share %，图例 pill 实时显示百分比一眼看出"活都让谁干了"；某账号颜色消失 = 被限流/熔断/冷却

3.3 事件刻度（细节加分项）

  • 429 / 熔断打开 / 熔断复活发生的那一秒，在 ①② 图底部画一个红色/橙色小刻度线——资源管理器没有、但对这个项目特别有用（把「限流排队生效」从数字变成看得见的时间点）。
  • 实现：history point 加一个 events 位掩码（1=429, 2=breaker open, 4=revive），零额外结构。

3.4 交互与放置

  • 新「监控」tab 注册进 TABS 数组；总览到达卡片下方加一行「实时监控 →」链接跳转。
  • 轮询只在监控 tab 激活 + 页面可见时跑（visibilitychange 暂停），切走即停——后台 NAS 上不留常驻流量。
  • canvas 常驻 DOM，轮询只 redraw() 不重建 innerHTML——避开现在整页 innerHTML 重渲染会闪的问题。

5风险与对策

风险对策
多人开监控页 → NAS 轮询放大history 读是 O(1) 快照拷贝；前端同一会话单轮询 + 页面不可见即停
每秒差分跨计数器回绕/重启差分保护：delta<0 视为计数器重置，记 0 并重置基线（单测覆盖）
账号频繁增删导致堆叠图错位按 account id 对齐 + 归一化 share；已删账号灰色折叠
canvas 高分屏模糊devicePixelRatio 缩放 + resize 监听（模板里已有同类处理习惯）
console.html 单文件继续膨胀图表引擎独立成 static/chart.js（go:embed 已支持多静态文件，引入成本为零）

6待你拍板的三个口径

  • 负载率分母：v1 只按 text 池（与现有比值同口径，最稳）；image/video 池要不要 v2 加模态切换 tab？
  • 默认窗口：60s（资源管理器默认感）还是 5min（更实用）？建议默认 60s、一键切 5min/1h。
  • 放置：独立「监控」tab（推荐，信息密度高不挤总览）还是嵌进总览 arrival 卡下面？
